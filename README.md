# Управление контекстом: окно, факты и ветки диалога (DeepSeek, Go + браузер)

Локальное приложение с веб-интерфейсом, в котором агент ведёт диалог, но
модель больше не получает историю «как есть». Что именно уйдёт модели,
решает стратегия, и стратегий здесь три:

- **скользящее окно** — только последние N сообщений, всё старше
  выбрасывается без замены;
- **карточка фактов** — отдельный блок «ключ — значение», который
  обновляется после каждой реплики пользователя; модели уходят факты плюс
  те же последние N сообщений;
- **ветки** — диалог как дерево: точка сохранения, два продолжения от
  одного места, переключение между ними. Ветка решает не «сколько истории
  уходит модели», а «какая история вообще существует».

Рядом с ними работает эталон — **вся история**: весь разговор заново
каждый ход. Без него сравнивать не с чем: «окно дешевле» ничего не значит,
пока неизвестно, сколько стоил бы тот же разговор целиком и что агент при
этом помнил бы.

Переключатель между стратегиями есть и в интерфейсе, и во флагах. В
одиночном диалоге стратегию можно сменить прямо посреди разговора:
сообщения при этом не трогаются, меняется только то, что из них уйдёт
модели на следующем ходе.

Интерфейс устроен как стенд: реплика уходит трём агентам сразу — тому,
кто помнит всё, тому, кто помнит последние сообщения, и тому, кто помнит
карточку фактов. Ответы, журналы, числа и уровень занятого контекста
стоят дорожка к дорожке, и разницу видно в тот же момент, когда она
возникает.

Развитие предыдущего задания: счёт токенов, свой лимит контекста, история
в JSON, агенты и инструменты Википедии и GBIF переехали почти без правок.
Новое — карточка фактов вместо конспекта, дерево веток с точками
сохранения, переключатель стратегий, новый агент-аналитик и опыт, в
котором один и тот же сбор технического задания прогоняется тремя
стратегиями, а рядом ставится отдельный опыт с ветвлением.

## Что нужно

- Go 1.22 или новее;
- ключ DeepSeek API (https://platform.deepseek.com);
- доступ в интернет к `ru.wikipedia.org` и `api.gbif.org` — только для
  агента-справочника, стратегиям он не нужен;
- любой современный браузер.

Флаги:

```bash
go run . -strategy full            # эталон: вся история каждый ход
go run . -strategy window          # только последние сообщения
go run . -strategy facts           # карточка фактов и последние сообщения (по умолчанию)
go run . -keep-messages 12         # размер окна в сообщениях
go run . -max-facts 30             # потолок числа записей в карточке
go run . -fact-value 300           # потолок длины одного факта в символах
go run . -facts-tokens 800         # потолок ответа извлекателя фактов
go run . -facts-model deepseek-v4-pro   # вести карточку другой моделью
go run . -context-limit 4000       # свой лимит контекста, чтобы поймать переполнение на коротком диалоге
go run . -on-overflow trim         # при переполнении выбрасывать старые ходы
go run . -keep-tools 0             # не сокращать старые ответы инструментов
go run . -history ./my-history     # другой каталог хранилища
go run . -addr 127.0.0.1:9000      # другой порт
go run . -open=false               # не открывать браузер
```

Два режима без интерфейса:

```bash
go run . -report examples/report.md   # прогнать опыт целиком и записать отчёт
go run . -report out.md -parallel=false  # сценарии по очереди, а не разом
go run . -probe-overflow              # отправить заведомо слишком длинный запрос и показать ответ API
```

## Три стратегии

### Скользящее окно

Модели уходят последние `-keep-messages` сообщений, всё старше просто
выбрасывается. Самая дешёвая и самая забывчивая стратегия: расход
контекста перестаёт расти с длиной диалога, но всё, что сказано в начале
разговора, исчезает без следа.

Граница окна режется не по счётчику сообщений, а по началу хода. Ответ
инструмента без вызова, который его породил, API отвергает: `tool` без
своего `assistant` с `tool_calls` — ошибка запроса. Поэтому граница
двигается вперёд до ближайшего сообщения пользователя, а если последний
ход сам длиннее окна (много вызовов инструментов), отступает назад к его
началу. Окно из-за этого редко ровно `keep` сообщений: оно целое, а не
заданного размера.

### Карточка фактов

Отдельный блок «ключ — значение», который живёт рядом с сообщениями и
уходит модели вместо начала истории:

```
цель: собрать ТЗ на систему учёта списаний
срок: первая версия к 1 марта 2027 года, сдвигать нельзя
бюджет: 1 200 000 рублей (согласован)
офлайн-режим: обязателен, на трёх точках отваливается интернет
не входит в первую версию: прогноз спроса, интеграция с кассой
```

Карточку ведёт отдельный запрос к модели — извлекатель. Он срабатывает
после каждой реплики пользователя, получает текущую карточку, хвост
диалога и новую реплику, а возвращает **правки**, а не карточку целиком:

```json
{"set": [{"key": "бюджет", "value": "1 200 000 рублей"}], "delete": ["старый бюджет"]}
```

Правки, а не новый текст — по двум причинам. Во-первых, видно, что именно
изменилось на этом ходе: список ключей уходит в журнал и в интерфейс.
Во-вторых, переписывая карточку целиком, модель может незаметно потерять
половину записей; заместить одно значение по ключу она потерять не может.

Что записывать, сказано в промпте извлекателя прямо: цель, ограничения,
предпочтения, принятые решения, договорённости о том, как отвечать, и
сведения о самом пользователе. Чего не записывать — тоже: предложения
агента, которые пользователь не подтвердил, справочные подробности и
рассуждения.

Ключи сравниваются без учёта регистра и краевых пробелов, а модели прямо
сказано переиспользовать существующие ключи дословно. Без этого карточка
раздваивается: «срок», «Срок» и «сроки» живут втроём и противоречат друг
другу.

Карточка не растёт бесконечно: `-max-facts` держит потолок записей,
`-fact-value` — длину значения. При переполнении извлекателю говорят
удалить лишнее самому, а если он этого не сделал, вытесняется самая давно
не обновлявшаяся запись. Это осознанная потеря, и число вытесненного
попадает в журнал.

Карточка уходит модели отдельным системным сообщением с пояснением —
«начало разговора не показано целиком, считай факты отсюда частью
диалога, саму карточку не пересказывай». Без пояснения модель принимает
карточку за реплику пользователя и начинает её обсуждать.

### Ветки

Диалог здесь не лента, а дерево.

- **Точка сохранения** запоминает место в ветке: сколько сообщений и
  ходов в её пути и какой была карточка фактов на этот момент.
- **Ветка** растёт из точки. Она хранит только свои сообщения и ссылку на
  родителя с местом ветвления; путь ветки склеивается на чтении — начало
  пути родителя до точки плюс собственные сообщения. Общая часть лежит в
  файле один раз.
- **Переключение** между ветками ничего не копирует и не удаляет: оно
  меняет то, какой путь уйдёт модели на следующем ходе.

Ветка видит путь до места ветвления и дальше только своё. Сообщений
соседней ветки в её контексте нет вообще — ни за деньги, ни по ошибке.
Поэтому ветвление решает задачу, которую ни окно, ни факты не решают:
разобрать два несовместимых варианта, не смешивая их в одном разговоре.

Ветвление работает при любой из трёх стратегий: сначала ветка задаёт
путь, потом стратегия решает, сколько от этого пути уйдёт модели.
Карточка фактов при ветвлении копируется из снимка точки — ветка
начинается с той памятью, какая была в месте ветвления, а не с нынешней,
и правки в одной ветке до другой не доходят.

## Переключатель

Стратегия — свойство диалога, а не настроек сервера. Так дорожки стенда
могут отличаться именно ею, а после перезапуска каждый диалог
продолжается по своим правилам.

Переключить её можно тремя способами:

- флагом `-strategy` при запуске — задаёт умолчание для новых диалогов;
- в интерфейсе при создании одиночного диалога;
- в интерфейсе прямо посреди разговора: кнопки «Вся история / Окно /
  Факты» над лентой.

Переключение ничего не портит. Сообщения остаются на месте — меняется
только то, что из них уходит модели. Карточка фактов остаётся в файле
диалога и снова заработает, если вернуться к `facts`; пока диалог идёт в
режиме окна, извлекатель не зовётся и денег не стоит.

## Как это устроено

```
main.go                 флаги, сборка зависимостей, запуск сервера
report.go               опыт: три стратегии на одном сценарии + опыт с ветвлением
internal/strategy       переключатель: режимы, границы окна, что уходит модели
internal/facts          карточка «ключ — значение» и извлекатель, который её ведёт
internal/history        диалог как дерево веток, точки сохранения, хранилище JSON
internal/agent          контракты агента, цикл хода, счётчики контекста
internal/agents         конкретные агенты: аналитик, справочник с инструментами, чат
internal/runs           диалоги в работе: ходы, стенд, ветвление, поток событий
internal/server         HTTP API и раздача фронтенда
internal/llm            клиент DeepSeek, расход и цены
internal/tokens         оценка числа токенов до отправки запроса
internal/tools          инструменты Википедии и GBIF
web/                    фронтенд, встроенный в бинарник
```

**Решение принимает арифметика, а не модель.** Ни извлекатель фактов, ни
граница окна не описаны модели как инструмент, и вызвать их она не может.
Зовёт их обвязка хода — `agents.run` — до обращения к модели. Инструмент
вызывался бы уже внутри хода, когда контекст отправлен и за старую
историю заплачено, то есть управлять им поздно. Плюс измеримость:
сравнение стратегий имеет смысл, только пока решение принимает счётчик, а
не настроение модели.

**Ход не падает из-за карточки.** Если извлекатель не ответил или вернул
не JSON, ход всё равно состоится: модель получит окно со старой карточкой,
а в журнале появится заметка. Оплаченный, но бесполезный запрос при этом
попадает в счёт карточки — платить за него пришлось.

**Версия карточки растёт только при настоящих правках.** Извлекатель
зовётся на каждой реплике, но «спасибо, понятно» новых фактов не
приносит. Если бы версия росла всё равно, начало запроса менялось бы
каждый ход и кэш префикса обнулялся бы впустую.

**Нулевая стратегия — это «вся история».** `strategy.Policy{}` не должна
молча начинать резать контекст и звать вторую модель: умолчание
приложения живёт во флагах, а не в нормализации нулевой структуры.

**Каждый ход считает две гипотезы даром.** Кроме самого запроса агент
оценивает, во что обошёлся бы тот же ход с полным путём ветки (столбец
«вся история») и во что — если бы веток не было вовсе и весь диалог шёл
одной лентой (столбец «одной лентой»). Обе оценки ничего не стоят и
превращают «стратегия экономит» в число.

## Стенд в браузере

Экран делится надвое: слева пульт, справа лента.

**Пульт** липнет к верху окна и не уезжает вместе с прокруткой — ветвиться
и переключать стратегию нужно с любого места разговора, а лента длинная.
В нём три блока:

- **Дерево диалога** (только у одиночного диалога). Ветки строками с
  отступом по глубине, под каждой — её точки, а под точкой — ветки,
  которые из неё выросли. Активная ветка отмечена линией слева и точкой у
  имени; клик по другой — перейти в неё. У строки точки две роли и два
  органа: клик по самой строке (⑂ и название) **прокручивает ленту к
  этому месту** и подсвечивает такт, кнопка «ветка» рядом отводит отсюда
  новую ветку. Сверху две кнопки: «⑂ Ветка отсюда» (точка на текущем
  конце ставится сама) и «Точка» (только пометить место, ветку завести
  позже).

  Место точки ищется по идентификатору хода, а не по его номеру: в ленте
  «весь диалог» ходы идут не по одной ветке, и номер там значил бы другое.
  Если место лежит в соседней ветке, лента сама переключается на «весь
  диалог» — там есть все ходы; если и там не нашлось, интерфейс говорит,
  в какой ветке искать.
- **Стратегия** — три кнопки столбиком, под ними правило выбранной.
  Переключается посреди разговора.
- **Журнал** — прошлые стенды и одиночные диалоги.

**Лента** — справа, вместе с шапками дорожек:

- **Шапки дорожек.** У каждой стратегии своё имя, свой цвет и
  вертикальная шкала занятого контекста. Шкалы в общем масштабе, поэтому
  их сравнивают взглядом; столбик разделён на служебную часть, историю
  дословно и карточку фактов. Пунктир поперёк — сколько ушло бы модели
  без стратегии, пунктир точками — сколько ушло бы без ветвления. Шапки
  тоже липкие: числа нужны на глазах, пока читаешь ленту.
- **Такты.** Реплика во всю ширину, под ней ответы дорожек, числа хода и
  журнал. Место ветвления отмечено швом: «дальше — ветка такая-то». Таким
  же швом, но в цвете стратегии, отмечена её смена: «дальше — стратегия
  „Вся история“». Стратегию можно переключить посреди разговора, и тогда
  соседние ходы сравнивать нельзя — у них разный контекст; каждый ход
  помнит, по какой стратегии шёл, и шов делает это видимым.
- **Граница окна** — пунктирная линейка поперёк ленты с подписью «выше
  модель не видит ничего: 12 сообщений отрезано окном» (у стратегии
  фактов — «выше дословной истории нет: … заменено карточкой фактов»).
  Она показывает край видимого на последнем ходе и с каждым новым ходом
  опускается: окно держит постоянный размер, а разговор растёт. На стенде
  черты нет — у трёх дорожек граница своя, и одна линия врала бы сразу
  про две.
- **Карточка фактов** показывается под последним ходом таблицей: ключ,
  значение и ходы, на которых факт появился и менялся последний раз.
  Модель видит именно её, а не начало списка сообщений. Счётчики дорожки
  включают ведение карточки: извлекатель — такой же запрос к модели, и в
  шапке рядом с «дорожка стоила» стоит «из них на карточку».

### Дерево против линейного диалога

Как только веток становится больше одной, над лентой появляются две
вкладки — это и есть сравнение прямо в интерфейсе:

- **«Путь ветки»** — то, что видит модель: унаследованная часть плюс своё.
  Под вкладками счёт: сколько в пути ходов и сообщений и сколько сообщений
  лежит в соседних ветках, не попадая в этот контекст вовсе.
- **«Весь диалог лентой»** — тот же разговор, каким он был бы, если бы
  ветвиться было нельзя: все ходы всех веток подряд, в одном потоке,
  каждый кусок подписан своей веткой. Этого потока модель не видела ни
  разу — ходы шли по веткам; здесь он собран для сравнения.

Там же стоит и цена: «на последнем ходе модель получила ≈1 632 токена
вместо ≈2 041, которые ушли бы одной лентой». Счётчик не считается
отдельно — агент оценивает эту гипотезу даром на каждом ходе.

Ветвление доступно в одиночном диалоге, а не на стенде: на стенде три
дорожки, и ветвить их пришлось бы синхронно втроём. Но дорожку стенда
можно открыть отдельно — «открыть отдельно →» в её шапке, — и тогда у неё
появляются и ветки, и переключатель; обратно возвращает «Вернуться на
стенд». Ходы, сделанные отдельно, в остальные дорожки не попадут, и стенд
перестанет идти в ногу — об этом сказано в подсказке кнопки.

Пока отвечает хоть одна дорожка, следующая реплика не уходит никому, а
ветвление и смена стратегии заблокированы: ход всё равно записался бы в
ту ветку, из которой стартовал.

## Опыт

`go run . -report examples/report.md` прогоняет обе половины опыта и
пишет отчёт в markdown; ход за ходом он же печатается в терминал. Готовый
отчёт с полными таблицами и всеми ответами лежит в
[`examples/report.md`](examples/report.md).

**Первая половина.** Один и тот же сбор технического задания из 18 ходов,
прогнанный тремя стратегиями. Агент — аналитик без инструментов: в опыте
важна работа с контекстом, а не работа с источниками. В первых ходах
пользователь называет себя, компанию, город, срок и бюджет, в середине
меняет решение о бюджете, а последние пять вопросов спрашивают о начале
разговора — к этому моменту его в окне уже нет. Сценарии идут
одновременно: диалоги независимы, а три прогона по 18 ходов подряд — это
втрое дольше.

**Вторая половина.** То же начало разговора до места, где надо выбрать
между двумя вариантами клиента. Дальше он расходится: в каждой ветке
разбирается свой вариант и фиксируется как выбранный, а потом в обеих
задаётся один и тот же вопрос — какой вариант мы выбрали. Рядом тот же
разговор идёт одной лентой: ветвиться нельзя, оба варианта лежат в одном
контексте. Стратегия у всех трёх дорожек — полная история, чтобы разница
в числах была разницей ветвления, а не обрезки.

Проверка памяти грубая и оттого честная: в ответе ищется имя, число или
слово, которое агент мог знать только из начала диалога. У неё есть цена
— она видит вхождение слова, а не смысл, — поэтому в отчёт кладутся и
сами ответы: числа показывают цену, а качество видно только глазами.

## Что показал опыт

Модель `deepseek-v4-flash`, температура 0, окно — 8 сообщений, карточка —
до 24 записей. Прогон от 13 сентября 2026 года.

| стратегия | вход, токенов | контрольные вопросы | стоил диалог | стоила карточка | всего | без кэша стоило бы |
|---|---|---|---|---|---|---|
| вся история | 28 364 | 14 из 14 | $0.002078 | — | $0.002078 | $0.007394 |
| окно | 17 593 | 2 из 14 | $0.002604 | — | $0.002604 | $0.004757 |
| факты | 25 905 | 14 из 14 | $0.003477 | $0.002686 | $0.006162 | $0.0117 |

**Окно снимает 38 % контекста и забывает почти всё.** Из четырнадцати
контрольных проверок оно прошло две — и обе потому, что нужная реплика
ещё не успела выйти из окна. Забывание при этом выглядит не как «не
помню», а как утверждение о мире: «В нашей переписке этого не было: вы не
называли ни своего имени, ни компании, ни города», «что в неё не входит,
не проговаривали — так что „не делать“ мы пока ничего не договорились».
И имя, и список того, что не входит в первую версию, пользователь назвал
прямым текстом; агент этого больше не видит и уверенно сообщает, что
этого не было.

**Карточка фактов снимает 9 % контекста и помнит всё.** Четырнадцать
проверок из четырнадцати — столько же, сколько у полной истории. К концу
разговора в карточке 16 записей на 1178 символов: имя, компания, город,
цель, пользователи, три причины списания, срок, бюджет, офлайн-режим,
авторизация, что не входит в первую версию. Это и есть вся память агента
о начале разговора — начала истории он не видит вовсе.

**Девять процентов — это средняя по диалогу, и она обманчива.** Первые
ходы стратегия не трогает вовсе: пока история короче окна, резать нечего,
и все три дорожки платят одинаково. Разрыв копится к концу: на последнем
ходе модель получила ≈1 508 токенов с карточкой вместо ≈2 513, которые
ушли бы с полным путём, — то есть 40 % с этого хода. У окна и фактов
расход перестаёт расти вместе с диалогом, у полной истории растёт
линейно, поэтому чем длиннее разговор, тем больше разрыв. Карточка при
этом сама занимает место: к концу диалога в ней 1178 символов, и они
уходят модели каждый ход.

**По деньгам карточка проиграла втрое.** $0.0062 против $0.0021 у полной
истории. Причин две, и обе видны в отчёте:

- извлекатель — это второй запрос к модели на каждом ходе. Восемнадцать
  запросов, 20 928 токенов, $0.0027 — почти половина всего счёта;
- любая стратегия ломает кэш префикса. У DeepSeek совпадающее начало
  запроса стоит в тридцать раз дешевле; пока история только дописывается
  в конец, префикс не меняется и 88 % входа идёт по цене кэша. Окно
  меняет начало запроса каждый ход, карточка — каждый раз, когда в ней
  что-то поправили; у обеих доля кэша падает до 55–60 %.

Поэтому в отчёте есть столбец «заплатили бы без кэша»: там та же экономия
видна в чистом виде — $0.0074 у полной истории против $0.0048 у окна.
У провайдера без кэширования префикса расклад был бы другим.

### Ветвление

| дорожка | своих ходов | вход, токенов | стоила | проверки |
|---|---|---|---|---|
| общая часть | 6 | 5 418 | $0.000551 | — |
| ветка «нативное приложение» | 3 | 4 278 | $0.000379 | 2 из 2 |
| ветка «PWA» | 3 | 4 296 | $0.000361 | 2 из 2 |
| тот же разбор одной лентой | 11 | 13 573 | $0.001213 | 0 из 1 |

Общая часть — 12 сообщений — оплачена один раз и досталась обеим веткам;
в файле она лежит в одном экземпляре.

**Ветки не смешались.** На один и тот же вопрос «какой вариант клиента мы
выбрали» ветка «нативное приложение» ответила про Kotlin и раздачу apk
через MDM и ни разу не упомянула PWA; ветка «PWA» — про service worker и
IndexedDB и ни разу не упомянула Kotlin. Так и должно быть: сообщений
соседней ветки в контексте нет вообще.

**Лента смешалась — и повела себя хуже всего.** В ней оба варианта
зафиксированы как выбранные один за другим, и агенту пришлось их
примирять: «Выбрали PWA… Важно: это решение заменило более раннее —
нативное Android-приложение на Kotlin». Формально связно, по сути —
выдумка: пользователь ничего не заменял, он разбирал два варианта.
Ветвление снимает не столько токены, сколько вот такие ответы.

**По токенам ветвление снимает заметно, но итог дешевле не выходит.**
Три хода ветки, у которых есть с чем сравнивать, обошлись в ≈4 639
токенов вместо ≈6 130, которые ушли бы на те же ходы одной лентой, —
меньше на ≈1 491, и разрыв растёт. Но весь опыт с ветками — это 12 ходов
и $0.00129, а лента — 11 ходов и $0.00121: контрольный вопрос в ветках
задаётся дважды, по разу в каждой. Ветвление окупается на длинных ветках,
а его главная ценность вообще не в цене.

## Сравнение стратегий

**Качество ответа.** Полная история и карточка фактов — 14 проверок из
14, окно — 2 из 14. Разницы в качестве между полной историей и фактами
на этом сценарии нет: карточка сохранила всё, о чём спрашивали. Разница
есть в форме: полная история отвечает подробнее и охотно вспоминает, как
менялось решение («ты подняла бюджет с 900 тысяч»), карточка отвечает
короче и только текущим значением.

**Стабильность.** Здесь окно проигрывает не тем, что молчит, а тем, что
уверенно отрицает: «мы этого не обсуждали» про то, что обсуждали десять
ходов назад. Отличить такой ответ от правды изнутри диалога нельзя — он
выглядит ровно как честное «сведений нет». Карточка устойчива
по-другому: в ней лежит ровно одно значение по ключу, и
отменённое решение не может всплыть как действующее — оно просто
замещено. Слабое место карточки — потолок записей: на очень длинном
разборе самый давний факт вытеснится, и это молчаливая потеря, её видно
только в журнале. Слабое место полной истории — контекст модели: рано
или поздно разговор в него не влезет.

**Расход токенов.** Окно — 38 % экономии, карточка — 9 % на восемнадцати
ходах; обе перестают расти с длиной диалога, полная история растёт
линейно. Деньги при этом устроены иначе, чем токены: на кэше префикса
дешевле всего оказалась полная история, а карточка — дороже всех, потому
что платит и за второй запрос, и за сломанный кэш.

**Удобство для пользователя.** Окно не требует ничего и ничего не даёт:
через десяток ходов собеседник перестаёт помнить, с чего начали. Карточка
— единственная стратегия, память которой можно прочитать: она лежит
таблицей «ключ — значение» под последним ходом, и видно, что именно агент
запомнил и на каком ходе. Это же и способ её исправить — ошибку в
карточке видно до того, как она испортит ответ. Ветвление — единственный
способ разобрать два несовместимых варианта, не заставляя агента
примирять их в одном контексте; цена — надо помнить, в какой ветке
находишься, поэтому активная ветка отмечена в шапке, в списке веток и
швом в ленте.

## Насколько точна оценка токенов

Оценщик из прошлого задания переехал без правок: он считает токены по
классам символов до отправки запроса, чтобы показать разбивку контекста и
поймать переполнение раньше API. Факт всегда берётся из `usage` ответа.

На этом сценарии оценка завышает: средняя ошибка 9.2 % на полной истории,
9.9 % на окне и 6.4 % на фактах; худший ход — 12.6 %. В прошлом задании
на диалоге про животных ошибка укладывалась в единицы процентов. Веса
подбирались там, и это ровно то, чем оценка по классам символов и
является — прикидкой, которую проверяет факт. Для своей задачи —
показать, из чего сложился контекст, и поймать переполнение до
отправки — точности хватает с запасом.

## Файл диалога

Один диалог — один JSON-файл в каталоге `history`. Дерево, точки и
карточка лежат в нём же:

```json
{
  "id": "6b1aecb70415b323",
  "strategy": "facts",
  "active": "9f2c…",
  "branches": [
    {
      "id": "7a1b…", "name": "основная",
      "messages": [ … ], "turns": [ … ],
      "facts": {
        "entries": [
          {"key": "бюджет", "value": "1 200 000 рублей", "since": 4, "turn": 10}
        ],
        "version": 13, "calls": 18, "usage": { … }, "cost": { … }
      }
    },
    {
      "id": "9f2c…", "name": "PWA",
      "parent": "7a1b…", "forkAt": 12, "forkTurn": 6,
      "messages": [ … ], "turns": [ … ], "facts": { … }
    }
  ],
  "checkpoints": [
    {"id": "c3d4…", "name": "перед выбором клиента", "branch": "7a1b…",
     "at": 12, "turn": 6, "after": "1f90…", "facts": { … }}
  ]
}
```

Сообщения хранятся целиком и никогда не режутся: стратегия сокращает
только то, что уходит модели. Ответы инструментов прошлых ходов
сокращаются до `-keep-tools` символов на отправке — в файле они остаются
полными.

Настоящий такой файл лежит в
[`examples/history`](examples/history): разбор ТЗ на три хода, точка
сохранения после третьего, две ветки от неё — «нативное приложение» и
«PWA», — по два хода в каждой и один и тот же вопрос в обеих. В конце у
него `"strategy": "window"`: диалог начинался с фактов, и стратегию
переключили посреди разговора, а карточка осталась в файле.

## API

```
GET    /api/agents                              каталог агентов, стратегия, каталог истории
GET    /api/conversations                       список диалогов
POST   /api/conversations                       новый диалог: {agent, text, strategy}
GET    /api/conversations/{id}                  диалог целиком: путь ветки, дерево, точки, карточка
DELETE /api/conversations/{id}                  удалить диалог со всеми ветками
POST   /api/conversations/{id}/turns            следующая реплика: {text}
POST   /api/conversations/{id}/checkpoints      точка сохранения: {name}
POST   /api/conversations/{id}/branches         ветка: {from, name}; пустой from — от текущего конца
POST   /api/conversations/{id}/switch           переключить ветку: {branch}
POST   /api/conversations/{id}/strategy         переключить стратегию: {strategy}
GET    /api/conversations/{id}/file             файл диалога как есть
POST   /api/comparisons                         новый стенд: {agent, text}
GET    /api/comparisons/{group}                 стенд целиком
POST   /api/comparisons/{group}/turns           реплика всем дорожкам сразу
GET    /api/turns/{id}                          состояние хода и журнал
GET    /api/turns/{id}/events                   поток событий хода (SSE)
```

Ветвление и смена стратегии отвечают диалогом целиком: интерфейсу не
нужно перечитывать его отдельным запросом.

## Тесты

```bash
go test ./...
go test ./... -cover
```

Сети в тестах нет: модель подставная (`internal/llm/llmtest`), инструменты
— заготовки. Проверяются границы окна, замещение фактов по ключу и разбор
правок извлекателя, живучесть хода при неудачном извлечении,
независимость веток и наследование пути, снимок карточки в точке
сохранения, переключение стратегии посреди диалога, сохранение дерева
между запусками и весь HTTP API.
